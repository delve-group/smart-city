| D014 / 2026-10-03 | Accepted: frontend structure `app/` (routing), `api/<service>/` (one endpoint per file, types, mappers), `features/<feature>/` (one folder per component, local hooks/utils), `shared/` | User requirement; one place for API communication and clear feature boundaries. Rules in `apps/frontend/AGENTS.md`. |
| D015 / 2026-10-03 | Accepted: PoC phase without tests; Vitest and existing unit tests removed | User request to focus on a working PoC. Verification is lint, type check, build and a manual review. Revisit once the product scope stabilises. |
| D016 / 2026-10-03 | Accepted: everything in English (docs, code, commits, UI copy); branches named `<type>/<description>` without a `codex/` prefix | User request. Replaces the earlier Polish-documentation rule and `codex/` branch convention. |
| D017 / 2026-10-03 | Accepted (PoC): event map interaction — search (events + Photon places), points fading in over the heatmap from street zoom, hover tooltip, non-modal detail panel (bottom sheet on phones); five `--category-*` colour tokens per theme | User request. Photon is free and keyless but fair-use only. Category colour is always paired with an icon and a text label. Demo events are fictional, placed at real venues and generated relative to the current time. |
| D018 / 2026-10-03 | Accepted: pivot from an event map to a resident issue-reporting map (reports with mandatory API-defined categories, filter, report flow); D017's event data is superseded | Matches the official task (failures and disruptions, resident–institution communication, urban data). Reporting is the core action; the heatmap shows where problems cluster. |
| D019 / 2026-10-03 | Accepted (PoC): demo backend as Next route handlers with an in-memory store; request validation shares the client's Zod schema | Lets the jury submit a report and see it on the map without a database. Data resets on restart and is per server instance — a database is the first backend step. |
| D020 / 2026-10-03 | Accepted: one neutral theme with light and dark mode replaces Civic and Signal; Geist typeface; radius 6 px, light shadows; colour only for categories, status and the heatmap (`--heat-*` tokens); mode follows the OS until toggled | User feedback: the previous palettes were too blue and too decorative; a neutral base reads as polished and professional and lets report colours stand out. The HTML preview in `design-system/` still shows the old themes and is obsolete. |
| D021 / 2026-10-03 | Accepted (PoC): "I'm affected too" — `POST /api/reports/:id/confirmations` adds one confirmation; at 3 a reported issue becomes Confirmed; resolved reports reject it. The browser remembers which reports it confirmed (localStorage) | Turns duplicates into weight, which feeds the heatmap and the city's priorities. Without accounts the server cannot stop repeat confirmations — a real backend needs identity or rate limits. |
| D022 / 2026-10-03 | Accepted (PoC): the base map is recoloured into the app's neutral greys through `--map-*` tokens (roads by contrast, a brief sand tint was rejected as off-palette); no live traffic layer yet | User asked for more colour on roads or traffic data. Free, keyless real-time traffic for Kraków does not exist; TomTom or HERE traffic tiles need an API key (free tiers exist) and Google traffic needs the Google Maps switch (D013). A traffic layer can be added as an optional overlay once a key is provided via `.env.local`. |
| D023 / 2026-10-03 | Accepted (PoC): 3D buildings from OpenMapTiles `render_height` behind a "3D" toggle; heatmap is a single rose hue; main roads get a faint warm accent | User request: 3D support, a subtle road accent, and the amber–red blobs looked ugly. One hue with translucent edges reads as density rather than alarm colours and no longer competes with the road tint or category colours. |
| D024 / 2026-10-03 | Accepted: "Create a report" replaces "Report an issue"; a settings popover holds the 3D and dark-mode switches; report points are icon markers | User request. "Report an issue" read like reporting a bug in the app. Grouping view options keeps the top bar to search and filter. Icons make categories readable without relying on colour alone. |
| D025 / 2026-10-03 | Accepted (PoC): at street zoom a report colours its building or a stretch of its road instead of a heatmap glow | User request. Matched from rendered OpenFreeMap features; tiles (max zoom 14) merge buildings into multipolygons sharing one id, so feature-state colouring lit whole blocks — the single footprint containing the report is copied into our own fill-extrusion layer instead. Matching only covers reports in view at zoom ≥ 14.5 and depends on tile geometry; a real backend should store the building/road id with each report. |
| D026 / 2026-10-03 | Accepted product direction, not implemented: distinguish resident reports from operational incidents; dispatcher, decision-maker and institution roles; official approval before external contact/ticket execution | User's discovery brief. Residents should not have to find the responsible department. Tool contracts and open choices are in the [discovery draft](../plans/2026-10-03-voice-incident-design.md). D021 describes current code; the draft proposes separating corroboration from verification. |
| D027 / 2026-10-03 | Accepted: browser voice first, phone number later; government identity remains a labelled demo mock | User confirmed browser-first intake during brainstorming. Reuses the map application and keeps telephony provisioning outside the first slice. |
| D028 / 2026-10-03 | Superseded by D030–D031; historical proposal: one outage response loop in one backend, typed actor tools, durable approvals/tickets and a voice-provider trial | A complete resident-to-institution feedback loop demonstrates the idea with fewer integration dependencies.
